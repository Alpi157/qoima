# Архитектура v1

## Что делает система

Владелец продаёт автозапчасти без торгового зала. Сейчас он:

1. ищет товар по артикулу;
2. оформляет продажу: кому продал и сколько штук;
3. печатает накладную;
4. вручную добавляет приход товара (артикул и количество).

Покупатели платят наличными или картой/Kaspi. Бренд обычно не указывается. У товара есть цена продажи.
Пользователь один. Сейчас около 70 видов товаров.

Первая версия делает ровно это, плюс вход по паролю, историю и ежедневные бэкапы.

Сознательно НЕ входит в v1: сканер штрихкодов, кассовые смены, терминалы, фискальные чеки
(интеграция с онлайн-кассой), интеграция с Kaspi, несколько складов,
автоматическая синхронизация с другими системами. Перед запуском доступен ручной импорт XLSX.

Важно: накладная из этой системы не является фискальным чеком онлайн-кассы.

## Схема

```
Браузер (ноутбук или телефон)
        │ HTTPS
        ▼
┌──────────────── VPS (Ubuntu 24.04) ────────────────┐
│  Caddy: HTTPS-сертификат и раздача фронтенда        │
│    ├── /       → React (собранные статические файлы)│
│    └── /api/*  → FastAPI (uvicorn)                  │
│                      │                              │
│                  PostgreSQL (только внутри docker)  │
│                                                     │
│  Каждую ночь: pg_dump → шифрование → копия вне VPS  │
└─────────────────────────────────────────────────────┘
```

В разработке: PostgreSQL в docker compose, FastAPI через `uv run uvicorn --reload`,
фронтенд через `npm run dev`. Vite проксирует `/api` на `localhost:8000`, поэтому фронт и API
работают как один источник (одинаковые cookie, нет проблем с CORS).

Одна установка обслуживает один бизнес. Мультиарендность не делаем.

### receipts и receipt_lines (приход)
receipts: `number` (bigint unique, из `document_counters`), `received_at`, `supplier` (text null),
`note`, `status` ('posted' | 'cancelled'), `cancelled_at`, `cancelled_by`, `cancel_reason`,
`created_by`, `created_at`.

receipt_lines: `receipt_id`, `product_id`, `qty` (int, check > 0), `unit_cost` (bigint null, check >= 0).
В API нового приёма `unit_cost` обязательна, 0 допустим. NULL остаётся для старых строк.

Первое заполнение остатков делается обычным приходом. При импорте XLSX поставщик «X2»,
примечание «Бастапқы қалдық, X2-ден көшіру».

### sales и sale_lines (продажа)
sales: `number` (bigint unique, из `document_counters`), `request_id` (uuid unique, защита от двойной отправки),
`customer_id` (null допустим только при полной оплате), `sold_at`, `total` и `paid_at_sale` (bigint),
`payment_method` (text null, cash/card), `note`, `status` ('posted' | 'cancelled'),
`cancelled_at`, `cancelled_by`, `cancel_reason`, `created_by`, `created_at`.

sale_lines: `sale_id`, `product_id`, `qty` (int, check > 0), `unit_price` (bigint, check >= 0),
`line_total` (bigint), `unit_cost` (bigint null, check >= 0). Цена подставляется из товара, но в строке её можно изменить.
Сохраняется та цена, по которой реально продали.
`paid_at_sale` находится в пределах от 0 до `total`. Если значение меньше `total`, нужен покупатель.

### customer_payments (оплаты покупателей)

`id` (bigint identity), `number` (bigint unique), `request_id` (uuid unique),
`customer_id` (обязательный внешний ключ), `paid_at` (timestamptz), `amount` (bigint > 0),
`payment_method` (text not null, cash/card, без server default),
`note`, `status` ('posted' | 'cancelled'), `cancelled_at`, `cancelled_by`,
`cancel_reason`, `created_by`, `created_at`. Номера выдаются через `document_counters`.
Оплата относится ко всему покупателю, а не к отдельной продаже.

Долг нигде не хранится. Он равен сумме `total - paid_at_sale` проведённых продаж покупателя
минус сумму его проведённых оплат и `debt_credit` проведённых возвратов
плюс сумму `amount` проведённых корректировок долга.
Отменённые документы исключаются. Отрицательное значение
означает переплату и допустимо, в том числе после отмены продажи.

### customer_debt_adjustments (17.5)

Документ «Қарызды түзету»: `id` (bigint identity), `number` (bigint unique),
`request_id` (uuid unique), обязательный `customer_id` (FK customers, индекс),
`adjusted_at` (timestamptz, индекс), `amount` (bigint, CHECK <> 0),
`reason` (text not null, CHECK непустой после обрезки пробелов), `status`
(posted/cancelled), `cancelled_at`, `cancelled_by`, `cancel_reason`,
`created_by`, `created_at`. Поля отмены и авторов следуют соглашению оплат.
Положительный amount увеличивает долг, отрицательный уменьшает. Проведённый
документ неизменяем, исправление выполняется отменой. Корректировки не входят
в выручку, прибыль, debt_given и received отчётов, не создают складских движений.

Номера без пропусков из счётчика `debt_adjustment`. Одна миграция `42b8e0f713ac`
после `31a7d9e602bf`. Первой командой downgrade блокируется таблица корректировок
и проверяются все документы, включая отменённые. При наличии документов выдаётся
русская ошибка с количеством и указанием восстановить бэкап через `deploy/restore.sh`.
Схема, счётчик и версия Alembic остаются прежними. Без корректировок downgrade
и повторный upgrade сохраняют прежние продажи, оплаты и возвраты.

### sale_returns и sale_return_lines (17.3a)

sale_returns: `id`, `number` (bigint unique, без пропусков, счётчик `return`),
`request_id` (uuid unique, `uq_sale_returns_request_id`), `sale_id` (FK sales, индекс),
`customer_id` (nullable FK customers, индекс, копия из продажи), `returned_at`
(timestamptz, индекс), `total`, `debt_credit`, `refund_amount` (bigint >= 0),
`refund_method` (nullable text, cash/card), `note`, `status` (posted/cancelled),
`cancelled_at`, `cancelled_by`, `cancel_reason`, `created_by`, `created_at`.
CHECK: `debt_credit + refund_amount = total`,
`(refund_amount > 0) = (refund_method IS NOT NULL)`,
`customer_id IS NOT NULL OR debt_credit = 0`.
Поля отмены следуют соглашению остальных документов.

sale_return_lines: `id`, `return_id` (FK sale_returns, индекс), `sale_line_id`
(FK sale_lines, индекс), `product_id` (FK products), `qty` (int > 0),
`unit_price` (bigint >= 0), `line_total` (bigint, CHECK `line_total = qty * unit_price`),
`unit_cost` (nullable bigint >= 0), `condition` (good/defective).
Цена и себестоимость копируются из строки продажи. Строка продажи встречается
в одном возврате не больше одного раза. Возвраты товара, позднее помещённого в архив,
разрешены. Проведённый возврат неизменяем; исправление выполняется отменой.

Одна миграция `31a7d9e602bf` после `2a7c9e41b603`. Первая команда downgrade
блокирует таблицу возвратов и проверяет число всех документов, включая отменённые.
Если возвраты есть, до изменений схемы выдаётся русская ошибка с их количеством
и указанием, что откат с ними возможен только восстановлением из резервной копии
через `deploy/restore.sh`. Схема и версия Alembic сохраняются. Без возвратов
прежние данные сохраняются при downgrade и повторном upgrade.

### document_counters (номера документов)
`doc_type` (text PK, check `IN ('receipt', 'sale', 'payment', 'return', 'debt_adjustment')`), `last_number` (bigint, check >= 0).
Одна строка на тип документа, `last_number` - последний выданный номер.

Номер берёт `app/numbering.py::next_number(db, doc_type)`:
`UPDATE document_counters SET last_number = last_number + 1 WHERE doc_type = :t RETURNING last_number`,
в той же транзакции, что и создание документа, без commit.

Почему не sequence: `nextval` не откатывается, и каждая неудачная попытка (нехватка товара,
повтор `request_id`, любая ошибка после получения номера) оставляла бы дыру в нумерации
накладных. Строка счётчика меняется транзакционно: при откате номер возвращается, при commit
закрепляется за документом. Блокировка строки `UPDATE` заставляет одновременные проведения
одного типа документа брать номера по очереди (для одного пользователя это не заметно).
Номер отменённого документа остаётся за ним и повторно не выдаётся.

### stock_movements (журнал движений)
| поле | тип | заметки |
|---|---|---|
| product_id | fk | |
| warehouse_id | fk | |
| qty | int not null, check <> 0 | + приход, − расход |
| unit_cost | bigint null, check >= 0 | себестоимость единицы этого движения |
| kind | text | 'receipt', 'receipt_cancel', 'sale', 'sale_cancel', 'adjustment', 'return', 'return_cancel' |
| doc_type, doc_id | text null, bigint null | ссылка на документ |
| note | text null | причина корректировки |
| created_by | fk users | |
| created_at | timestamptz | |

Триггер запрещает UPDATE и DELETE.

### stock_balances (текущие остатки)
PK (`product_id`, `warehouse_id`), `qty int not null check (qty >= 0)`,
`avg_cost bigint null check (avg_cost >= 0)`. NULL означает неизвестную себестоимость.
Обновляется только функцией `inventory.service.post_movements` в той же транзакции,
что и вставка движений. Тест проверяет: остаток всегда равен сумме движений.

### business_settings (Шаг 12)
Реквизиты для накладной по форме З-2. Ровно одна строка: `id smallint PK CHECK (id = 1)`,
её создаёт миграция. `seller_name` (организация или ИП), `seller_iin_bin`, `responsible_person`
(ответственный за поставку), `released_by_name` (расшифровка подписи «Отпустил»; пусто - в
накладной имя пользователя, проводившего продажу), `chief_accountant` (расшифровка подписи
главного бухгалтера) - `text not null default ''` (пустая строка = не заполнено);
`updated_at timestamptz`.
API: `GET /api/settings`, `PUT /api/settings` (все поля обязательны, строки обрезаются;
ИИН/БИН пустой или ровно 12 цифр; остальные поля до 255 символов).

## Ключевые алгоритмы

### Импорт товаров и начальных остатков (17.4)

Команда `uv run python -m app.cli import-products PATH --user USERNAME` проверяет файл,
печатает сводку и предупреждения без записи. `--apply` выполняет импорт одной транзакцией
с одним commit. Рабочие файлы с настоящими ценами находятся в корневой папке `import/`,
исключённой из git. В репозитории только синтетический пример
`backend/tests/fixtures/qoima-import-example.xlsx`.

Лист «Товары», первая строка содержит точные заголовки в любом порядке:

| Заголовок | Значение |
|---|---|
| Артикул | обязательный; числовой читается как текст без конечного .0 |
| Название | обязательное |
| Единица | шт, компл., пара, л, кг, м, упак.; пусто означает шт |
| Цена продажи, ₸ | обязательное целое не меньше 0, в тенге |
| Закупочная цена, ₸ | целое не меньше 0; обязательна при положительном остатке |
| Остаток | целое не меньше 0; пусто означает 0 |
| Мин. остаток | пусто или целое не меньше 0 |
| Примечание | необязательное |

Все заголовки, кроме «Примечание», обязательны. Остальные колонки и листы игнорируются.
Строки с пустыми распознаваемыми полями пропускаются. Формулы не поддерживаются.
Применяются ограничения существующих схем товаров и приёмов: артикул до 64 символов,
название до 255, примечание до 1000, остаток до 100 000, минимальный остаток до 2 147 483 647,
каждая цена до 1 000 000 000 тенге.

Сначала проверяется весь файл, пользователь и наличие нормализованных артикулов в базе,
включая архивные товары. Все ошибки собираются с номером строки Excel и колонкой;
ошибки заголовков относятся к строке 1, ошибки пользователя к `--user`. При ошибках записей нет,
команда возвращает ненулевой код. Повторный импорт отклоняется по всем существующим артикулам.

Сводка: товаров, товаров с остатком, всего единиц, стоимость остатка по закупочным и
продажным ценам. Предупреждения: закупочная цена не меньше продажной и нулевой остаток.
Цены переводятся в целые тиыны до расчётов. Только вывод CLI для человека форматирует
тенге с пробелами по тысячам и, при необходимости, двумя цифрами тиынов без округления.
API и база используют целые тиыны.

Создание товаров использует общую логику каталога. Положительные остатки проводятся через
общую логику приёма и `post_movements`, поэтому `avg_cost` равна закупочной цене.
Нулевые остатки не создают строки приёма. Более `MAX_LINES` (200) строк разбиваются на
несколько приёмов с поставщиком «X2» и примечанием «Бастапқы қалдық, X2-ден көшіру».
Если положительных остатков нет, приёмы не создаются. Любая ошибка записи откатывает
весь импорт, включая складские движения и номера документов. После успеха выводятся номера приёмов.

### Нормализация артикула
1. Unicode NFKC, верхний регистр.
2. Кириллические буквы-двойники заменяются латинскими:
   А→A, В→B, Е→E, Ё→E, К→K, М→M, Н→H, О→O, Р→P, С→C, Т→T, У→Y, Х→X.
3. Остаются только A-Z, 0-9 и оставшиеся кириллические буквы. Пробелы, дефисы, точки,
   слэши и прочие символы удаляются.
4. Буква O и цифра 0 НЕ считаются одинаковыми.

Примеры: `ос-90` → `OC90`, `OC 90` → `OC90`, `0986.452.041` → `0986452041`, `ab/12_3` → `AB123`.

### Поиск товара
Запрос нормализуется. Результаты в порядке: точное совпадение артикула, артикул начинается с запроса,
артикул содержит запрос, похожесть названия (pg_trgm). Архивные товары скрыты. По умолчанию
50 результатов (`limit`), максимум 200, дальше постранично через `offset`.
В ответе есть остаток и цена.

### Проведение продажи (одна транзакция)
1. Если продажа с таким `request_id` уже есть: при том же составе вернуть её со статусом 200
   и ничего не создавать; при другом составе 409 «Этот запрос уже использован для другой
   продажи». Состав: покупатель, итоговая оплата при продаже, способ оплаты и набор строк
   (товар, количество, явно переданная цена). Порядок строк не важен.
2. Проверить покупателя и строки (товар существует, не повторяется, не в архиве).
   `unit_price` обязателен в каждой строке; 0 допустим, отсутствие или NULL даёт 422.
3. Создать продажу и строки, посчитать итог на сервере (`line_total = qty * unit_price`).
4. Через `post_movements` записать движения с минусом и обновить остатки: он блокирует строки
   `stock_balances` (`SELECT ... FOR UPDATE`, по возрастанию product_id) и при нехватке бросает
   409 «Недостаточно товара. OC-90: на остатке 2, требуется 3». Транзакция откатывается целиком,
   продажа не остаётся.
5. Номер берётся из `document_counters` при создании продажи (шаг 3), поэтому неудачная
   продажа номер не расходует. Один commit, ответ 201. Если два одинаковых запроса пришли одновременно, второй получает
   нарушение `uq_sales_request_id`, откатывается и возвращает продажу первого (шаг 1).

### Скользящая средняя себестоимость (17.2a)

`stock_balances.avg_cost` хранит среднюю закупочную цену в целых тиынах.
Она меняется только в `post_movements` вместе с остатком под той же блокировкой
`stock_balances FOR UPDATE`. Блокировки берутся в прежнем порядке.
Проверка нехватки использует суммарную дельту товара за весь вызов;
состав `insufficient_stock.items` и текст ошибки не меняются.
Для расчёта средней движения одного товара применяются по входному порядку.

Обозначения: `n` текущий остаток, `a` средняя, `q` положительное количество,
`c` закупочная цена строки. Округление половины вверх для неотрицательных чисел:
`round_half_up(N, D) = (2*N + D) // (2*D)`, где `D > 0`. Float не используется.

- Приход с известной ценой: при `a IS NULL` или `n = 0` новая средняя равна `c`;
  иначе `round_half_up(n*a + q*c, n+q)`.
- Приход без цены сохраняет среднюю; в движение записывается текущая средняя.
- Отмена прихода с известной ценой (`receipt_cancel`, `return_cancel`): `n_next = n-q`. При `n_next = 0` или неизвестной
  средней она сохраняется. Иначе `N = n*a-q*c`; при `N < 0` средняя сохраняется,
  при `N >= 0` становится `round_half_up(N, n_next)`.
  Отмена старого приёма без цены тоже сохраняет среднюю.
- Продажа и корректировки в обе стороны сохраняют среднюю;
  себестоимость движения равна текущей средней.
- Отмена продажи возвращает товар по исторической `sale_lines.unit_cost` и использует
  формулу прихода. Неизвестная цена возврата сохраняет среднюю.

`stock_movements.unit_cost` сохраняется при вставке. `sale_lines.unit_cost` берётся
из соответствующего движения продажи и является неизменным снимком.
Поздние приёмы и их отмены снимок продажи не пересчитывают.
Годный возврат использует формулу прихода по исторической цене строки продажи.
`return` и `return_cancel` сохраняют этот снимок в движениях, включая NULL;
при неизвестной цене средняя сохраняется. Брак не создаёт движений.
Нулевая цена известна; NULL означает, что цена неизвестна.

Миграция заполняет среднюю существующих остатков средневзвешенной ценой известных
строк всех проведённых приёмов товара, включая товары с нулевым остатком.
Отменённые приёмы и неизвестные цены исключаются. При отсутствии известных цен
средняя остаётся NULL. Старые движения и снимки продаж не заполняются задним числом.

### Способ оплаты (17.2a)

`cash` означает наличные, `card` карту/Kaspi без интеграции с банком.
При положительной оплате продажи пропущенный или NULL способ превращается в `cash`.
При нулевой оплате способ равен NULL; явный способ вызывает 422 `validation_error`.
CHECK продажи: `(paid_at_sale > 0) = (payment_method IS NOT NULL)`.
Нулевая сумма продажи также не имеет способа оплаты.
Оплата долга получает `cash` по умолчанию; NULL в ней запрещён.
Идемпотентность обоих документов сравнивает итоговый способ оплаты.
Ответы продажи, списка продаж, оплат и ledger содержат `payment_method`.
В записи продажи ledger способ равен NULL, если оплаты при продаже не было.

### Стоимость склада и пороги (17.2a)

`ProductOut` содержит `min_qty`, `avg_cost` основного склада и `last_cost`.
Последняя известная цена берётся из строк с `unit_cost IS NOT NULL` только проведённых
приёмов по `received_at DESC`, затем id строки DESC. Поздняя строка с NULL или
отменённый приём её не заменяют. Ноль является известной ценой.
В списках, поиске и частых товарах дополнительные запросы на каждый товар не выполняются.

`out` означает остаток 0, включая отсутствие строки остатка.
`low` означает заданный `min_qty` и `0 < stock <= min_qty`.
При `stock_state` архивные исключаются даже с `include_archived=true`.
PATCH `min_qty: null` отключает порог.

`GET /api/stock/summary` одним SQL-запросом считает по неархивным товарам основного склада:
`products_count`, `total_qty`, `cost_value = sum(qty*avg_cost)` по известным ценам,
`retail_value = sum(qty*sale_price)`, `unknown_cost_count` при `qty > 0` и неизвестной средней,
`out_of_stock_count`, `low_stock_count`. Отсутствующий остаток равен нулю.

### Отчёты (17.2a)

Все три маршрута защищены и требуют `from`/`to` в формате YYYY-MM-DD.
Оба дня включены по Asia/Almaty. Конец не раньше начала, максимум 366 календарных дней;
нарушения дают 422 `validation_error`. Только проведённые документы входят в расчёт.

Summary возвращает `revenue`, `sales_count`, `cost`, `profit`, `revenue_unknown_cost`,
`debt_given`, `returns_total`, `returns_count`, `defect_loss`,
`received {cash, card, total}`, `days [{date, revenue, profit}]`.
`cost = sum(qty*unit_cost)` по известным снимкам, `profit` равна выручке этих же строк
минус cost. Выручка неизвестных строк учитывается отдельно. Неизвестная цена не равна нулю.
`debt_given = sum(total-paid_at_sale)` продаж периода.
`received` объединяет оплаты при продаже по `sold_at` и оплаты долгов по `paid_at`;
минус `refund_amount` возвратов по `returned_at` и `refund_method`.
Отменённые документы исключаются. Период только с возвратами может иметь
отрицательные выручку и received. Days отсортирован по возрастанию даты, содержит нулевые дни.

Products возвращает `{items, total}` с `product_id, article, name, unit, qty, revenue,
cost, profit, revenue_unknown_cost`. Customers возвращает `{items, total}` с
`customer_id, name, sales_count, revenue, profit, revenue_unknown_cost`; продажи без покупателя объединены
в одну строку с NULL id и именем. Исторические продажи архивных товаров сохраняются.
Сортировка: revenue по убыванию, затем id по возрастанию; NULL покупателя при равенстве последним.
Пагинация: limit по умолчанию 50, максимум 200; offset по умолчанию 0.
Каждый ответ выполняет один или два SQL-запроса данных, без N+1.

Единый источник `_sales_source` объединяет строки продаж по `sold_at` и
отрицательные строки проведённых возвратов по `returned_at`. Возвраты уменьшают
количество в отчёте товаров независимо от состояния товара.
Годная строка вычитает `line_total`; при известной себестоимости также
`qty*unit_cost` из cost и `line_total-qty*unit_cost` из profit.
Бракованная строка вычитает `line_total` из revenue и profit по известной цене,
не изменяя cost: расход исходной продажи сохраняется. При неизвестной цене
оба вида возвратов вычитают `line_total` из `revenue_unknown_cost`, cost/profit не меняют.
`defect_loss` равен сумме `qty*unit_cost` бракованных возвращённых строк с известной ценой.
Полный годный возврат вместе с продажей даёт revenue/profit 0; полный возврат брака
даёт revenue 0 и profit минус себестоимость продажи.

Summary агрегирует финансовые строки по их собственной дате отдельно от заголовков
документов; суммы денег не умножаются на число строк. `returns_total` и
`returns_count` относятся к проведённым возвратам периода. `sales_count` в summary
и customers считает только продажи периода, возвраты его не увеличивают.
День с одним возвратом имеет sales_count 0. `debt_given` сохраняет исходное
значение суммы `total-paid_at_sale` проведённых продаж периода.

### Отмена документа
Продажа: статус 'cancelled', обратные движения 'sale_cancel'. Повторная отмена запрещена.
Если есть проведённый возврат, `sale_has_returns`: сначала отменить все возвраты.
Проверка выполняется под блокировкой строки продажи. Возврат отменяется обратными
движениями годных строк `return_cancel`; нехватка даёт `return_cancel_blocked` с items.
Брак не создаёт обратных движений. Повторная отмена даёт `return_already_cancelled`.
Отмена исключает debt_credit из формулы долга автоматически.
Приход: то же с 'receipt_cancel', но если товар уже продан и остаток уйдёт в минус, отмена запрещена
с понятным сообщением.
Корректировка долга: статус cancelled, повторная отмена запрещена. Отмена
положительной корректировки разрешена даже при отрицательном итоговом долге.
Оплата: статус 'cancelled', повторная отмена запрещена. Отмена продажи разрешена после оплаты;
пересчитанный долг может стать отрицательным.

### Блокировки долга и идемпотентность документов

Операции, меняющие долг покупателя, сначала блокируют его строку `customers` через
`SELECT ... FOR UPDATE`. Затем продажа берёт номер и блокировки остатков по возрастанию
`product_id`, отмена продажи блокирует строку продажи и остатки, оплата берёт номер,
отмена оплаты блокирует строку оплаты. Корректировка берёт номер после проверки
долга, её отмена блокирует покупателя, затем документ корректировки. Возврат и его отмена блокируют покупателя исходной продажи, затем продажу,
затем возврат при отмене и остатки по возрастанию product_id/warehouse_id.
Новый возврат берёт номер после проверки количества и денег, до складских движений.
При отсутствии покупателя первая блокировка приходится на продажу.
Каждая операция завершает одну транзакцию одним commit.
Оплата проверяет долг после блокировки покупателя. Сумма оплаты не может превысить положительный
долг. Для повторного `request_id` сравниваются покупатель, сумма, способ оплаты и нормализованная заметка;
явный `paid_at` сравнивается как момент времени с учётом часового пояса. Пропущенный `paid_at`
не сравнивается, поскольку сервер назначает текущее время и повторный запрос не может его знать.
В продаже сравниваются покупатель, итоговый `paid_at_sale`, способ оплаты и строки с явно переданными ценами;
заметка и дата не входят в прежний состав идемпотентности.

### Приём и корректировка остатка: идемпотентность (22)

POST /api/receipts и POST /api/stock/adjustments требуют request_id UUID.
Первое проведение возвращает 201, повтор того же состава — 200 с сохранённым
документом без повторных движений и расхода номера. Изменённый состав даёт 409:
`receipt_request_conflict` или `stock_adjustment_request_conflict`.
Старые receipts.request_id и stock_movements.request_id остаются NULL;
ReceiptOut возвращает nullable request_id. Отменённый приём также возвращается повтором.

Приём сравнивает набор строк (product_id, qty, unit_cost) без учёта порядка,
supplier и note после обрезки пробелов и преобразования пустого текста в NULL.
received_at сравнивается как момент времени, только если задан и не NULL.
Корректировка сравнивает product_id, знаковый qty и reason после обрезки пробелов.
Её повтор возвращает то же движение и текущий остаток, который мог измениться позже.

Перед поиском повтора берётся транзакционная блокировка
pg_advisory_xact_lock(namespace, hashtext(request_id::text)):
namespace 2201 для приёма, 2202 для корректировки остатка. Она удерживается до
завершения транзакции. Затем выполняются проверки, номер и складские блокировки
в прежнем порядке. Коллизия хеша только сериализует независимые UUID;
поиск и сравнение всегда используют полный UUID.
Уникальность страхуют uq_receipts_request_id и частичный индекс
uq_stock_movements_request_id WHERE request_id IS NOT NULL. IntegrityError
перехватывается только для своего ограничения, с rollback и повторным чтением.
Другие документы не заполняют request_id складского движения.

Оплата проверяет повтор до блокировки покупателя и повторно после её получения,
до проверки долга. Повтор оплаты всего долга возвращает исходную оплату,
даже если первый запрос уже обнулил долг.

### Денежные границы запросов (22)

MAX_MONEY = 10**15 тиынов (10 трлн ₸), меньше 2**53. Оплата долга и оплата
продажи ограничены MAX_MONEY, корректировка долга — ±MAX_MONEY,
expected-суммы возврата — от 0 до MAX_MONEY. Все значения остаются строгими
целыми, без float и bool. Цены единицы сохраняют MAX_SALE_PRICE.
Продажа требует unit_price каждой строки, включая явный 0: текущая цена
товара не подставляется и не участвует в проверке повтора.
Сервисы продажи и приёма проверяют qty × цену каждой строки и итог документа:
превышение MAX_MONEY даёт 422 `amount_too_large`, «Сумма слишком большая».
Граница включительная. Ограничение отдельного документа не ограничивает
накопленные суммы остатков, отчётов и долга.

### Проведение корректировки долга (17.5)

POST принимает request_id, customer_id, amount, reason, adjusted_at?. Amount
строгий ненулевой integer в диапазоне от -MAX_MONEY до MAX_MONEY, без float и bool. Reason обрезается
по краям, от 3 до 500 символов как общая причина документа. Дата aware,
допускает прошлое и максимум минуту в будущем. Отсутствие или NULL означает сейчас.

После блокировки покупателя сумма отрицательной корректировки по модулю не должна
превышать текущий долг, иначе 409 `debt_adjustment_exceeds_debt` с params
{debt, amount}, где amount сохраняет знак запроса. При нуле или переплате
уменьшение запрещено. Положительное увеличение не ограничивается текущим долгом.
Номер берётся после проверки. Один commit, ошибка откатывает всю операцию.

Повтор request_id всегда сравнивает customer_id, amount и нормализованный reason.
Заданный adjusted_at сравнивается как момент времени; отсутствующий не сравнивается.
Проверка повтора выполняется до блокировки и снова после её получения, до расчёта
долга. Повтор возвращает документ с 200, даже если он отменён; другой состав
даёт 409 `debt_adjustment_request_conflict`. Гонка уникальности обрабатывается
только для uq_customer_debt_adjustments_request_id с rollback и повторным чтением.

### Проведение возврата (17.3a)

POST получает request_id, sale_id, returned_at?, note?, refund_method? и
строки {sale_line_id, qty, condition}. Не принимает цену или себестоимость.
В 17.3b добавлены необязательные expected_debt_credit и expected_refund_amount:
оба целых неотрицательных значения в тиынах передаются вместе или не передаются.
NULL считается незаданным значением; неполная пара даёт 422 validation_error
с типом return_expected_split_pair. Верхняя граница каждого значения MAX_MONEY.
Продажа должна быть posted. Количество строки не больше проданного минус сумма
возвращённого по posted-возвратам, включая брак. Ошибка `return_qty_exceeds_sold`
содержит article, sold, returned, requested. Чужая строка даёт полевую 422
`sale_line_not_in_sale`; повтор строки даёт `duplicate_line` с document=return.
Дата aware, допускает прошлое и максимум одну минуту вперёд; дата раньше sold_at
даёт 422 с типом `returned_at_before_sale`, включая дату по умолчанию.

Деньги рассчитываются по текущему долгу после блокировки покупателя:
`debt_credit = min(total, max(долг, 0))`, `refund_amount = total-debt_credit`.
Если expected-суммы переданы, они сравниваются с рассчитанными после блокировки
покупателя, до проверки refund_method, получения номера и записи изменений.
Расхождение даёт 409 return_split_changed с params {debt_credit, refund_amount},
содержащими новые суммы. Документ не создаётся и номер не расходуется.
Изменение долга без изменения деления суммы разрешает сохранение.
Без покупателя debt_credit 0. При положительном refund_amount пропущенный
или NULL refund_method становится cash. При нулевом денежном возврате явный
способ запрещён: 422 validation_error, тип `refund_method_without_refund`.
Нельзя молча игнорировать способ, поскольку итог зависит от долга внутри транзакции.

Expected-суммы в сравнение повтора не входят: сохранённый документ возвращается
до проверки расчёта, даже если ожидания клиента изменились.
Идемпотентность возврата всегда сравнивает sale_id, набор строк
(sale_line_id, qty, condition) без учёта порядка и note после обрезки пробелов
по краям и преобразования пустой строки в NULL. returned_at сравнивается как
момент времени, refund_method с сохранённым способом, только если значения заданы;
NULL равен отсутствию. Изменение состава даёт `return_request_conflict`.
Повтор возвращает сохранённый документ с 200, даже после отмены, без пересчёта денег.
Проверка повтора выполняется до блокировок и повторно после их получения.
Гонка уникального request_id обрабатывается через IntegrityError только на
uq_sale_returns_request_id, с rollback и повторным чтением документа.

### Статус оплаты накладной (17.3a)

Статус и остаток не хранятся. Для каждой проведённой продажи i покупателя:

```text
d_i = total_i - paid_at_sale_i
own_i = сумма debt_credit проведённых возвратов этой продажи
applied_i = min(d_i, own_i); d'_i = d_i - applied_i; leftover_i = own_i - applied_i
пул кредитов = проведённые оплаты + сумма leftover_i + сумма abs(отрицательных корректировок)
позиции долга = d'_i накладных + amount положительных корректировок
cum_j = накопленная сумма позиций по (дата документа, kind, id)
outstanding_j = min(позиция_j, max(0, cum_j - пул кредитов))
net_total_i = total_i - сумма total проведённых возвратов этой продажи
```

payment_status: `returned`, если net_total_i = 0; иначе `paid`, если
outstanding_i = 0; `unpaid`, если outstanding_i >= net_total_i; иначе `partial`.
Приоритет returned применяется буквально и при изначально нулевом итоге.
Кредит возврата сначала уменьшает долг его собственной накладной; только остаток
входит в общий FIFO. Например A 5 000 и B 10 000 в долг: полный возврат B оставляет
A unpaid с outstanding 5 000, а B returned с outstanding 0.

Положительная корректировка занимает отдельную позицию по adjusted_at: начальный
долг старше накладных закрывается первым. При одинаковой дате kind=adjustment
предшествует sale, затем порядок по id. У продаж дата sold_at. Отрицательные
корректировки входят в общий пул независимо от даты.

Инвариант: для любого покупателя сумма outstanding его проведённых продаж
и положительных корректировок равна max(долг из общей функции, 0). Отменённые продажи получают null в outstanding
и payment_status. У проведённой продажи без покупателя outstanding 0, статус
returned при net_total 0, иначе paid.

Общий SQL-источник FIFO с оконными функциями в customers/service.py используется
сервисом продаж в деталях и списке. Остатки корректировок доступны внутри
источника; API корректировок не добавляет поле outstanding.
Все posted-документы участвуют независимо от дат; backdated-оплаты тоже входят
в пул. Фильтры и пагинация применяются после расчёта. Список без N+1.
Фильтр open включает только unpaid/partial и исключает returned.
SaleOut.lines содержит id и returned_qty только по posted-возвратам;
SaleOut.returns содержит id, number, returned_at, total, status всех возвратов.

### Формат ошибок API

Каждый ответ 4xx содержит `detail`, `code` и `params`. `code` - машинный код в snake_case,
`params` - данные сообщения (объект, по умолчанию пустой). `detail` - русский текст для логов
и отладки. Фронтенд принимает решения только по `code`, а текст для пользователя собирает
по `code` и `params` из `errors.*` в текущем языке; если перевода для кода нет, показывает `detail`.
Схема тела `ErrorOut` и список кодов `ErrorCode` есть в OpenAPI (ответ `4XX` у каждого эндпоинта),
на фронтенд они попадают через `make gen-api`.

Бизнес-ошибка (`AppError` из `app/errors.py`): текст, код и параметры. Код задаётся атрибутом
`code` у класса исключения; у каждого наследника `AppError` свой код (проверяет тест).
Параметры передаются вторым аргументом: `ProductArchivedError(текст, {"article": ...})`.

```json
{"detail": "Товар OC-90 в архиве", "code": "product_archived", "params": {"article": "OC-90"}}
```

Ошибка валидации запроса (422 от Pydantic): общий текст, код `validation_error` и список полей.

```json
{
  "detail": "Проверьте введённые данные",
  "code": "validation_error",
  "params": {},
  "errors": [
    {"field": "lines.0.qty", "message": "Должно быть не меньше 1",
     "type": "greater_than_equal", "params": {"ge": 1}},
    {"field": "note", "message": "Максимальная длина: 1000",
     "type": "string_too_long", "params": {"max_length": 1000}}
  ]
}
```

`field` - путь к полю через точку; у полей тела без префикса `body`, у параметров пути и
строки запроса с префиксом (`path.sale_id`, `query.limit`), у тела целиком пустая строка.
`type` - тип ошибки Pydantic (`missing`, `string_too_long`, `less_than_equal`, ...) или свой тип.
`params` - значения из контекста ошибки, только числа, строки и списки (`ge`, `le`, `gt`, `lt`,
`min_length`, `max_length`, `expected`, ...). Фронтенд переводит поле по `type` и `params` из
`validation.*`. `message` - русский текст; перевод типов Pydantic в `VALIDATION_MESSAGES`
(`app/errors.py`), неизвестный тип даёт «Некорректное значение».

Свои типы (`PydanticCustomError` в схемах, список в `CUSTOM_VALIDATION_TYPES`):

## Фронтенд

Маршруты: `/login`, `/sale` (главный экран), `/products`, `/products/:id`, `/customers`,
`/customers/:id`, `/receipts`, `/receipts/new`, `/receipts/:id`, `/sales`, `/sales/:id`,
`/sales/:id/print`, `/settings`.

Главный экран продажи работает с клавиатуры: поле поиска артикула в фокусе, Enter добавляет товар,
количество и цена редактируются в строке, покупатель выбирается или создаётся тут же,
«Провести и напечатать» открывает накладную.

Каждая страница - отдельный чанк (`React.lazy` в `pages/lazyPages.tsx`), загружается при первом
заходе. Пока чанк грузится, `Suspense` показывает `PageLoader`: в `AppLayout` на месте
содержимого (меню остаётся), в `main.tsx` на весь экран (вход, печать накладной).

Накладная (`/sales/:id/print`) повторяет форму З-2 «Накладная на отпуск запасов на сторону»
(приложение 26 к приказу Министра финансов РК от 20.12.2012 № 562). Это отдельная страница вне
общего меню со стилями для печати A4 книжной (`InvoicePrintPage.css`: `@page`, повтор шапки
таблицы, строки не разрываются). Браузер печатает её или сохраняет в PDF. `?auto=1` открывает
диалог печати один раз после загрузки и убирает флаг из адреса. Реквизиты берутся из
`/api/settings`, количество и сумма прописью - `lib/amountInWords.ts`. Отменённая продажа
печатается с диагональной надписью «ОТМЕНЕНА».

### Языки интерфейса (Шаги 14 и 15)

Интерфейс на казахском, русском и китайском: i18next + react-i18next, ресурсы собраны в бандл
(`src/i18n/locales/ru.json`, `kk.json`, `zh.json`), `fallbackLng: 'ru'`. Все видимые тексты
лежат в `ru.json` по разделам: common, nav, auth, products, customers, receipts, sales, settings,
errors, validation, invoice. Ключи называются по смыслу (`sales.new.submit`), множественное число
через `count` (`_one`, `_few`, `_many`, `_other`), данные только интерполяцией `{{name}}`,
ссылки внутри фразы через `<Trans>`. Ключи в `t()` проверяются TypeScript по `ru.json`
(`src/i18n/i18next.d.ts`), а `npm run i18n:check` ищет ключи из кода, которых нет в `ru.json`,
лишние ключи в `ru.json` и печатает процент перевода kk и zh. Для kk и zh он падает, если ключа
не хватает, есть лишний или в переводе другой набор `{{переменных}}` и `<тегов>`, чем в русской
строке. Формы множественного числа берутся из `Intl.PluralRules` языка (ru: one/few/many/other,
kk: one/other, zh: other), ключи `invoice.*` в kk и zh не нужны.

Единица товара хранится в базе как есть, по-русски («шт», «компл.», …). Интерфейс показывает её
подпись на текущем языке (`unitLabel` в `lib/labels.ts`, ключи `common.units.*`), неизвестная
единица показывается как есть, в накладной остаётся русская.

Mantine обрезает многоточием подписи `Badge` и `SegmentedControl`; в `theme.ts` они переносятся
на следующую строку, чтобы длинные казахские слова не терялись на телефоне.

Язык: после входа - `users.locale` (`PATCH /api/auth/me` при смене в шапке); до входа -
выбор, сохранённый в localStorage (`qoima.language`), иначе язык браузера, иначе `kk`.
Вместе с языком меняются `<html lang>`, локаль dayjs для календарей Mantine (`kk`, `ru`, `zh-cn`)
и формат дат через Intl (`lib/dates.ts`). Деньги одинаковы для всех языков: «12 500 ₸».

Ошибки API: `apiErrorText` (`src/i18n/errorText.ts`) берёт `errors.<code>` с `params`, без
перевода показывает `detail`; ошибка поля - `validation.<type>` с `params`, иначе `message`.
Вариант текста выбирается контекстом i18next: `params.document` у `duplicate_line`, имя поля
у ошибок валидации (`validation.date_in_future_sold_at`).

Накладная всегда на русском: её тексты в `invoice.*`, страница берёт их через
`i18n.getFixedT('ru')`, дату форматирует по-русски. Панель над накладной следует языку.

## Безопасность

- Пароли: argon2. Вход ограничен: не больше 5 неудачных попыток в минуту с одного IP.
  Счётчик попыток хранится в памяти процесса, поэтому backend работает в одном процессе
  uvicorn (без `--workers N` и без нескольких реплик).
- Сессия: случайный токен в cookie `qoima_session` (`HttpOnly`, `SameSite=Lax`, `Secure` в продакшне), 30 дней без продления.
  В базе хранится только хэш токена.
- Изменяющие запросы принимают только JSON.
- PostgreSQL не доступен из интернета. Секреты только в `.env` (на сервере `deploy/.env.prod`),
  которые не попадают в git.
- IP клиента для лимита входа: uvicorn запущен с `--proxy-headers` и доверяет `X-Forwarded-For`
  только от контейнера Caddy (`FORWARDED_ALLOW_IPS`, фиксированный адрес в
  `deploy/docker-compose.prod.yml`). Caddy без `trusted_proxies` заменяет присланный клиентом
  `X-Forwarded-For` настоящим адресом, поэтому подделка заголовка лимит не обходит.
- Caddy добавляет HSTS, CSP, `X-Frame-Options: DENY`, `nosniff`, Referrer-Policy и убирает
  заголовок `Server`. На проде `ENABLE_DOCS=false`: `/docs`, `/redoc`, `/openapi.json` отключены.
- Сервер: SSH только по ключу, ufw (22, 80, 443), fail2ban, автоматические обновления безопасности.

## Бэкапы

Каждую ночь в 03:00 `deploy/backup.sh`: `pg_dump -Fc` (сжатый формат) из контейнера `db`,
шифрование `age` открытым ключом владельца, хранение 14 дней на сервере. Приватного ключа на
сервере нет. `deploy/pull-backups.sh` забирает бэкапы на компьютер владельца (rsync по SSH).
Раз в месяц пробное восстановление `deploy/restore.sh` в отдельную базу `qoima_restore_check`
со сверкой количества строк. Подробности в `deploy/README.md`.

## Хостинг

VPS у казахстанского провайдера: в базе имена и телефоны покупателей, это персональные данные.
1-2 vCPU, 2 ГБ RAM, Ubuntu 24.04, свой домен для HTTPS.

Продакшн-стек (`deploy/docker-compose.prod.yml`): `db` (postgres:17, volume, порт не публикуется),
`api` (`backend/Dockerfile`: python:3.12-slim, uv, непривилегированный пользователь; при старте
`alembic upgrade head`, затем один процесс uvicorn), `web` (`deploy/web.Dockerfile`: сборка
фронтенда в node, затем caddy:2-alpine со статикой и `deploy/Caddyfile`; порты 80, 443, 443/udp).
Установка на сервер по шагам: `deploy/README.md`.

# План работ

Каждый шаг заканчивается файлом `review/review-step-NN.zip` (см. «Завершение задачи» в AGENTS.md).
Человек отправляет zip на ревью, после одобрения делает коммит. Следующий шаг начинается
только после коммита предыдущего.

Шаги 1 и 18 человек делает руками. Остальные делает агент.

---

## Шаг 1. Среда разработки (руками)

WSL2 Ubuntu, Docker, git, uv, Node.js LTS, Claude Code, VS Code с расширением WSL,
репозиторий на GitHub. Готово, когда в `~/projects/qoima` работает `claude`.

## Шаг 2. Скелет проекта

**Что входит**
- Структура папок из `docs/architecture.md`: `backend/`, `frontend/`, `deploy/` (пока пустая, с .gitkeep).
- `docker-compose.yml` с сервисом `db` (postgres:17, healthcheck, именованный volume, порт 5432 только на 127.0.0.1).
  При первом запуске создаётся и основная база, и тестовая `qoima_test` (init-скрипт).
- `.env.example` со всеми нужными переменными (DATABASE_URL, TEST_DATABASE_URL, COOKIE_SECURE и т.д.).
- Backend: `pyproject.toml` (uv), `app/main.py`, `app/config.py`, `app/db.py`, `app/errors.py`.
  Эндпоинт `GET /api/health` возвращает `{"status": "ok", "db": "ok"}` и реально проверяет базу (`SELECT 1`).
- Alembic настроен, берёт URL из настроек. Первая миграция включает расширение `pg_trgm`.
- pytest: `conftest.py` прогоняет миграции на `qoima_test`, каждый тест в транзакции с откатом.
  Тест на `/api/health`.
- ruff настроен в `pyproject.toml`.
- Frontend: Vite + React + TypeScript + Mantine (с русской локалью), React Router, TanStack Query.
  Одна страница показывает «API: ok» или ошибку по ответу `/api/health`. Прокси `/api` на `localhost:8000`.
  ESLint и Prettier, скрипты `npm run lint`, `npm run build`, `npm run format`.
- Скрипт `npm run gen:api`, который генерирует типы из `http://localhost:8000/openapi.json` в `src/api/schema.ts` (openapi-typescript).
- `Makefile` с целями: `db`, `backend`, `frontend`, `migrate`, `test`, `lint`, `review STEP=NN`.
- `.github/workflows/ci.yml`: ruff, pytest с сервисом postgres, lint и build фронтенда.
- `README.md`: как запустить проект с нуля.
- Обновить раздел «Команды» в CLAUDE.md.

**Не входит**: таблицы товаров, авторизация, любая бизнес-логика.

**Готово, когда**: `make db`, `make migrate`, `make backend`, `make frontend` запускают проект,
в браузере на `localhost:5173` видно «API: ok»; `make test` и `make lint` зелёные; `npm run build` проходит.

## Шаг 3. База данных и ядро склада

**Что входит**
- SQLAlchemy-модели и миграция для: users, sessions, products, customers, warehouses (+ запись «Основной»),
  receipts, receipt_lines, sales, sale_lines, stock_movements, stock_balances, sequences для номеров документов.
- Все ограничения из `docs/architecture.md` (check, unique, fk, индексы, триггер на stock_movements).
- `catalog/normalize.py` с функцией `normalize_article` и тестами на все примеры из архитектуры и крайние случаи.
- `inventory/service.py`: `post_movements(db, movements, user_id)` с блокировкой строк остатков,
  созданием недостающих строк остатков, проверкой «не уходить в минус» и понятной ошибкой.
- Тесты: движение увеличивает и уменьшает остаток; минус запрещён; UPDATE и DELETE движений
  падают на уровне базы; инвариант «остаток равен сумме движений» после серии операций.

**Не входит**: эндпоинты (кроме health), авторизация.

**Готово, когда**: миграция применяется на чистую базу и откатывается `alembic downgrade base`; тесты зелёные.

## Шаг 4. Вход в систему

**Что входит**
- `auth/service.py`: хэширование argon2, создание и проверка сессий (хэш токена в базе, срок ровно 30 дней от входа).
- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`.
- Зависимость `current_user`, подключённая ко всем роутерам кроме health и login.
- Ограничение попыток входа: 5 в минуту с IP (в памяти процесса).
- Cookie `HttpOnly`, `SameSite=Lax`, `Secure` берётся из настроек.
- `app/cli.py`: `create-user` и `set-password` (пароль вводится без эха).
- Тесты: успешный вход, неверный пароль, неактивный пользователь, просроченная сессия, выход, лимит попыток,
  защищённый эндпоинт без cookie отвечает 401.

**Готово, когда**: пользователя можно создать командой и войти через `/docs` Swagger; тесты зелёные.

## Шаг 5. API товаров и покупателей

**Что входит**
- Товары: создание, получение, изменение, архивирование, поиск по алгоритму из архитектуры (с остатком в ответе).
- Дубликат артикула после нормализации даёт ошибку 409 с текстом, какой товар уже существует.
- Цены принимаются и отдаются в тиынах.
- Покупатели: создание, получение, изменение, поиск по имени.
- Тесты на всё, включая поиск `ос-90` → `OC90` и порядок результатов.

**Готово, когда**: всё проверяется через Swagger; тесты зелёные.

## Шаг 6. API прихода и корректировок

**Что входит**
- `POST /api/receipts`: строки (product_id, qty, unit_cost необязательно), поставщик, заметка. Проводится сразу.
- Список с фильтром по датам, просмотр, отмена с проверкой, что остаток не уйдёт в минус.
- `POST /api/stock/adjustments`: изменение остатка на +N или −N с обязательной причиной.
- `GET /api/products/{id}/movements`: история движений товара с номерами документов.
- Тесты: приход увеличивает остаток; отмена возвращает; отмена после продажи запрещена; корректировка без причины запрещена.

**Готово, когда**: через Swagger можно завести начальные остатки и увидеть историю товара; тесты зелёные.

## Шаг 7. API продаж

**Что входит**
- `POST /api/sales`: request_id, покупатель (необязательно), строки (product_id, qty, unit_price), заметка.
  Итог считается на сервере. Алгоритм проведения из архитектуры.
- Повтор с тем же request_id возвращает ту же продажу без дублей.
- Список с фильтрами (даты, покупатель), просмотр, отмена с обратными движениями.
- Тесты: продажа уменьшает остаток; нехватка товара даёт понятную ошибку и ничего не создаёт;
  повтор request_id; отмена; повторная отмена запрещена; итог считается верно.

**Готово, когда**: полный сценарий «приход → продажа → отмена» работает через Swagger; тесты зелёные.

## Шаг 14. Инфраструктура языков

Интерфейс готовится к трём языкам: казахскому, русскому и китайскому. Внешне ничего не меняется,
все тексты остаются русскими; появляется только переключатель языка.

**Что входит**
- Бэкенд: `users.locale` (`kk`, `ru`, `zh`, по умолчанию `kk`, CHECK в базе). `GET /api/auth/me`
  возвращает `locale`, `PATCH /api/auth/me {locale}` меняет его. CLI `create-user --locale`.
- Бэкенд: у `AppError` появляются `params`, ответ ошибки `{detail, code, params}`. `detail`
  остаётся русским текстом для логов и отладки. `params` заполнены у всех ошибок с данными
  (`insufficient_stock: {items: [{article, available, requested}]}` и т.д.), таблица в
  `docs/architecture.md`. У ошибок валидации в `errors` кроме `field` и `message` есть `type`
  (тип ошибки Pydantic) и `params` (ограничения из ctx: `ge`, `le`, `max_length` и т.п.).
- Фронтенд: i18next + react-i18next, ресурсы в бандле: `src/i18n/locales/ru.json`, `kk.json`,
  `zh.json` (kk и zh пока пустые, `fallbackLng: 'ru'`). Все видимые тексты вынесены в `ru.json`
  по разделам (common, nav, auth, products, customers, receipts, sales, settings, errors,
  validation, invoice), ключи по смыслу. Плюралы через `count`, данные только интерполяцией.
- Фронтенд: текст ошибки API собирается по `code` и `params` из `errors.*` в текущем языке,
  без перевода показывается `detail`. Ошибки полей по `type` и `params` из `validation.*`.
- Выбор языка: после входа из `users.locale`; до входа сохранённый в localStorage, иначе язык
  браузера, иначе `kk`. Переключатель «Қазақша / Русский / 中文» на странице входа и в шапке,
  после входа смена сохраняется через `PATCH /api/auth/me`. `<html lang>` меняется вместе с языком.
- Даты через Intl в текущем языке, локали dayjs для Mantine dates: kk, ru, zh-cn. Деньги
  одинаково для всех языков: «12 500 ₸».
- Накладная всегда на русском (`getFixedT('ru')`), `amountInWords` не меняется.
- `npm run i18n:check`: каждый ключ из кода есть в `ru.json`, в `ru.json` нет лишних ключей,
  процент заполнения kk и zh. В `make lint` и CI (падает только из-за ru).
- Тесты на locale, params ошибок, сборку текста ошибок, переключатель и русскую накладную.

**Не входит**: сами переводы на казахский и китайский, изменения дизайна.

**Готово, когда**: интерфейс выглядит как раньше; переключатель меняет `<html lang>` и после
входа сохраняет язык в базе; `make test`, `make lint`, `npm run build` зелёные.

## Шаг 16. Простой интерфейс для владельца

Упростить интерфейс под повседневную работу владельца: крупные элементы, меньше лишних полей
и шагов в частых операциях (продажа, приход, поиск товара), удобство на телефоне. Подробное описание
экранов, темы и текстов: `docs/design/simple-ui.md`, образец внешнего вида:
`docs/design/prototype.dc.html`. Шаг делится на три части.

### Шаг 16.1. Каркас: тема, шапка, главный экран, Тағы

**Что входит** (разделы «Тема», «Каркас», «Маршруты», «Главный», «Тағы» в simple-ui.md)
- Тема Mantine: шрифт Fira Sans из `@fontsource` (без внешних запросов), цвета, скругления,
  основной шрифт 18px, кнопки не ниже 56px, заметный фокус.
- Боковое меню убрано. Шапка: «Qoima», «Басты бет», переключатель языка, имя, «Шығу»;
  на узком экране язык и «Шығу» в выпадающем меню. Ссылка «← Тағы» вверху подробных разделов.
- Маршруты: `/` главный экран (и после входа), `/more` «Тағы»; временно `/sell`, `/receive`,
  `/stock` показывают старые экраны продажи, прихода и списка товаров; `/sale` → `/sell`.
- Главный экран: приветствие, три плитки, полоса «Бүгін» из `GET /api/sales` за сегодня.
- Вход в той же теме. В настройках кнопка «Нет бухгалтера».
- Бэкенд для 16.2: `GET /api/products/frequent`, `GET /api/customers/recent`.

**Готово, когда**: после входа открывается главный экран, все подробные разделы доступны через
«Тағы» и возвращаются по «← Тағы», старые экраны работают; `make test`, `make lint`,
`npm run build` зелёные.

### Шаг 16.2. Продажа в три шага

**Что входит** (разделы «Продажа, шаг 1-3», «Продажа сохранена», «Черновики» в simple-ui.md)
- `/sell?step=1|2|3`: товары с «Жиі сатылатындар», покупатель с «Соңғы сатып алушылар»,
  проверка; `/sell/done/:id` с печатью накладной.
- Черновик продажи в localStorage для каждого пользователя, с request_id.

**Готово, когда**: продажа проводится за три шага мышью, черновик переживает перезагрузку,
повторная отправка не создаёт дубль; тесты зелёные.

### Шаг 16.3. Приём товара, склад, причины отмены (выполнено в составе 16.2)

**Что входит** (разделы «Приём товара», «Товар принят», «Склад», «Отмена документа» в simple-ui.md)
- `/receive` с созданием нового товара прямо из поиска, блоком «Қосымша» и черновиком;
  `/receive/done/:id`.
- `/stock` «Қоймада не бар?»: поиск и таблица остатков.
- Быстрые причины в окне отмены документа.

**Готово, когда**: приём и склад работают по описанию, отмена принимает быструю причину;
тесты зелёные.
